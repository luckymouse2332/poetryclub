# CHORE-2 已合并分支清理与保留规则

## 背景

仓库长期保留了已经合入 `master` 的功能和修复分支，使本地、GitHub `origin` 与 CNB `mirror` 的分支列表包含大量不再承载工作的开发分支。现有工作流一处要求历史分支保留，另一处要求合入后删除，发布分支是否长期保留也不清楚。本任务统一分支生命周期并清理已经合入的冗余开发分支。

## 范围

- [x] 明确 `master`、`release/v*`、未合并工作分支和已合并开发分支的保留边界。
- [ ] 删除本地、`origin` 和 `mirror` 中已经合入 `master` 的普通开发分支。
- [x] 在开发工作流中写明删除前的合入校验和禁止擅自合并规则。

## 非目标

- [x] 不合并当前或其他尚未合入的工作分支。
- [x] 不删除 `master`、`release/v*`、稳定标签或当前尚未合入的 M5 通知分支。
- [x] 不修改现有提交历史、标签指向或发布内容。

## 架构边界

本任务只修改仓库治理文档和 Git 分支引用，不改变产品代码、数据库、部署配置或运行时行为。删除开发分支前必须确认其 tip 已经可以从 `master` 到达；不能为了满足清理目标而创建合并提交。尚未合入或是否废弃不明确的分支必须保留，等待负责人单独决定。

## 验收条件

- [ ] 本地、`origin` 和 `mirror` 不再保留已经合入 `master` 的 `feat/*`、`fix/*` 等普通开发分支。
- [ ] `master`、历史 `release/v*` 和当前尚未合入的 M5 通知分支保持不变。
- [x] `docs/development-workflow.md` 明确已合并开发分支立即删除、发布分支保留和禁止擅自合并。
- [ ] 工作区干净，远端分支列表与新规则一致。

## 发布影响

- 预期版本影响：`无需单独发布`
- migration / 环境变量 / 部署顺序：无。
- 兼容性与回滚边界：被删除分支的提交已经进入 `master`，仍可通过提交历史和标签恢复；文档规则可通过普通回滚提交撤销。

## 测试

运行 `pnpm check:conventions`，并使用 `git branch --merged`、`git branch -r --merged`、`git ls-remote --heads` 核对本地与两个远程的分支状态。

## 风险 / 回滚

误删未合并分支可能丢失唯一的远端引用，因此删除目标必须同时通过 `origin/master` 与 `mirror/master` 的祖先检查。已合并分支仍可从 `master` 历史恢复；若需恢复远端分支，可从原 tip 提交重新创建。
