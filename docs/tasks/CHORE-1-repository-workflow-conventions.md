# CHORE-1：仓库工作流与发布规范

## 背景

仓库已经实际使用 `feat/*`、`fix/*`、`release/v*` 分支、Conventional Commits 风格提交和 `v1.0.0`、`v1.1.0` 标签，但没有统一文档或自动检查。任务编号、分支名和发布版本之间也缺少明确边界，`package.json` 的 `0.1.0` 已与最新稳定标签 `v1.1.0` 不一致。

本任务建立一套向后兼容的仓库工作流。历史分支、提交和标签保留原样，新工作从本任务完成后遵守新规则。

## 范围

- [x] 明确路线任务、缺陷、运维、仓库维护和调查原型任务的编号规则。
- [x] 明确普通工作分支、发布分支和热修复分支的命名与生命周期。
- [x] 采用 Semantic Versioning 2.0.0 定义稳定版和 RC 标签。
- [x] 采用 Conventional Commits 风格定义提交标题、类型、scope 和破坏性变更说明。
- [x] 增加不依赖第三方包的分支、提交和发布检查脚本。
- [x] 增加 GitHub Pull Request、`master` 推送和发布标签检查。
- [x] 增加 Pull Request 模板，并同步 `AGENTS.md`、`README.md` 和任务清单。
- [x] 将 `package.json` 版本同步到当前稳定标签，并建立 `CHANGELOG.md`。

## 非目标

- [ ] 不修改历史提交、历史标签或现有远程分支名称。
- [ ] 不在本任务中创建新产品功能、数据库 migration 或生产部署。
- [ ] 不引入 Changesets、semantic-release、commitlint、Husky 等额外依赖。
- [ ] 不自动推送、合并、打标签或发布 GitHub Release。

## 架构边界

规范检查使用 Node.js 标准库和 Git 命令，不能进入应用运行时、客户端 bundle 或生产容器入口。GitHub Actions 只读取仓库内容和 Git 历史，不使用生产密钥。任务编号、Git 分支和 SemVer 发布版本保持独立，不能通过编号相似性推导发布版本。

## 验收条件

- [x] 新文档可以明确回答任务编号、分支命名、提交信息和版本升级方式。
- [x] `M4.1` 可以继续用于“内容访问权限”，本任务使用 `CHORE-1`，两者不会冲突。
- [x] 合法与非法分支名、提交信息和发布标签具有可重复执行的检查结果。
- [x] PR 分支和提交、`master` 新提交、`v*` 标签均有对应 CI 检查。
- [x] 当前 `package.json` 与 `v1.1.0` 对齐，`CHANGELOG.md` 记录已有稳定版。
- [x] 历史中不符合新规范的名称被明确视为保留历史，不要求重写。

## 测试

规范检查器自检、当前分支与最新提交检查、`v1.1.0` 稳定标签检查、TypeScript、ESLint、196 个单元测试、`db:check` 和带占位邮件配置的生产构建均通过。集成测试尝试执行但因本机 PostgreSQL 未监听 `127.0.0.1:5432` 而无法连接；本任务没有数据库行为或 migration，未因该环境阻断继续修改。GitHub Actions 需要在远程仓库事件中执行，本地仅完成静态审查。

## 发布影响

- 预期版本影响：`无需单独发布`
- migration / 环境变量 / 部署顺序：无。
- 兼容性与回滚边界：历史名称保持有效，新检查只约束本任务完成后的新工作。

## 风险 / 回滚

主要风险是规则过严导致正常分支或自动生成的合并、回滚提交被拒绝。检查器需要允许 GitHub 生成的合并提交和 Git 自动生成的回滚提交，同时对普通人工提交保持严格。回滚时可以移除检查脚本、CI、模板和新增文档；`package.json` 版本若回退，必须同时确认它仍与当前稳定标签一致。
