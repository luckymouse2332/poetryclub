# 修复bug

## 背景

管理后台用户卡片中的“作品”统计显示为“草稿 0 · 已发布 0”，但数据库中对应用户实际存在诗作。只读核对表明 `poem` 表总数与直接 SQL 聚合一致，问题位于 `listAdminUsers` 使用的 Drizzle 相关子查询：外层用户列在原始 SQL 片段中没有得到可靠限定，导致统计条件错误。

## 范围

- [x] 修正管理员用户列表中的草稿和已发布作品统计。
- [x] 为有作品和无作品用户增加真实 PostgreSQL 集成测试，并验证用户卡片显示。
- [x] 运行类型检查、lint、单元测试和相关集成测试。

## 非目标

- [x] 不修改诗作状态语义、治理状态或公开可见性规则。
- [x] 不重构管理员用户卡片、分页或筛选界面。
- [x] 不清理现有测试账号和测试诗作数据。

## 架构边界

统计查询继续位于 `src/server/services/moderation.ts`，页面和组件不直接访问数据库。查询必须按 `poem.authorId = user.id` 和 `draft | published` 作者状态聚合，隐藏状态不改变作者作品计数。不得读取无界作品列表后在应用内计数。

## 验收条件

- [x] 有一个草稿和一个已发布作品的用户显示“草稿 1 · 已发布 1”。
- [x] 没有作品的用户仍显示“草稿 0 · 已发布 0”。
- [x] 用户筛选、分页和其他管理功能不受影响。
- [x] 统计测试在真实 PostgreSQL 上通过。

## 测试

增加 `listAdminUsers` 集成测试，创建隔离用户和两种状态的作品后直接验证服务返回值，并在测试结束后删除夹具；管理员 E2E 验证卡片显示实际统计。运行 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm test:integration` 和相关 Playwright 用例。

## 风险 / 回滚

主要风险是聚合连接产生重复用户行或影响分页。修复采用按作者预聚合后再左连接用户列表的方式，保证每名用户至多一行；回滚时可恢复原统计表达式，不涉及 Schema 或 migration。

## 实际完成情况

问题已复现：专用 E2E 用户在数据库中有 1 个草稿，原 `listAdminUsers` 却返回 0。原实现把外层 `user.id` 放进手写相关子查询，生成查询时没有得到可靠限定。现改为先按 `poem.authorId` 聚合草稿和已发布数量，再左连接到分页用户列表；无作品用户通过 `coalesce` 保持为 0。

`pnpm typecheck`、`pnpm lint` 和 196 个单元测试通过。`pnpm test:integration` 为 2 个文件、4 个测试全部通过，其中新增测试验证 1 个草稿加 1 个已发布作品返回 1/1、无作品用户返回 0/0。管理员治理 Playwright 为 9/9 通过，新增用例验证卡片显示“草稿 0 · 已发布 1”。生产构建完成编译后，在类型阶段受到正在运行的本地开发服务器持续写入 `.next/dev/types` 的影响而失败；独立 TypeScript 检查已通过，本任务没有停止该服务器或删除其运行文件。
