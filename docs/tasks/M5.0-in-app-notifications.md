# M5.0 可扩展站内通知与系统公告

## 背景

当前项目已经具备作品治理、账号状态和管理员角色变更，但用户只能通过页面状态被动发现这些结果。产品调查将审核、封禁、权限相关的站内消息列为基础能力。M5.0 建立可扩展的通知核心，并为后续评论、回复、点赞和收藏事件提供稳定接入边界。

## 范围

- [x] 新增通知事件、通知收件人和系统公告数据模型及版本化 migration。
- [x] 接入作品隐藏/恢复、账号禁用/恢复、角色变更通知。
- [x] 实现公告草稿、受众选择、发布和审计。
- [x] 实现通知页、未读数量、导航下拉、已读操作和分页。
- [x] 使用 Redis Pub/Sub 与 SSE 提供在线用户的实时唤醒。
- [x] 更新 Compose、环境变量、部署、产品、架构和设计系统文档。

## 非目标

- [ ] 不实现评论、回复、点赞、收藏等互动功能本身。
- [ ] 不实现邮件、短信、浏览器推送、移动端推送或离线消息队列。
- [ ] 不实现已发布通知或公告的编辑、撤回和删除。
- [ ] 不引入逐用户公告筛选、定时发布或独立后台服务。

## 架构边界

- 通知业务位于 `src/features/notifications`，数据库与服务端逻辑位于 `src/server`，`src/app` 只保留路由和页面组合。
- 通知事件以文本类型和结构化 payload 保存，收件人关系独立保存已读状态；PostgreSQL 是权威来源。
- 所有入口独立执行身份认证、对象级授权、Zod 校验、业务规则校验和错误处理。
- suspended 用户可以读取和更新自己的通知已读状态，但不能修改诗作、角色或账号治理状态。
- SSE 仅发送当前用户的最小事件提示；Redis 是唯一的实时唤醒通道，应用通过 Compose 健康检查控制生产启动顺序。
- 用户正文和公告正文按纯文本展示，公告链接只允许站内相对路径。

## 验收条件

- [x] 通知、收件人和公告 migration 可重复检查并能在干净数据库中通过。
- [x] 治理状态变化、审计日志和通知在同一事务中提交，重复事件不会重复投递。
- [x] 公告草稿可编辑，发布时支持全部账号、全部 active、active member、active admin 四种受众，并生成发布时的收件人快照。
- [x] 已发布公告不可编辑、撤回或删除，发布动作可在审计页追溯。
- [x] 用户可以分页查看通知、筛选未读、点击目标后标记已读、手动标记无链接通知和全部已读。
- [x] 登录用户导航显示未读数量和最近通知，SSE 在线连接可以收到新通知提示，断线重连后能从数据库恢复。
- [x] 匿名用户不能访问通知页、SSE 或公告管理入口，用户不能读取或修改其他用户的通知。

## 发布影响

- 预期版本影响：`MINOR`
- migration / 环境变量 / 部署顺序：新增 Drizzle migration、`REDIS_URL` 和 Redis Compose 服务；先启动并检查 PostgreSQL、Redis，再执行 migration，migration 成功后启动 app。
- 兼容性与回滚边界：保留既有 PostgreSQL 数据卷和 `deploy/.env.production`；代码回滚前需确认通知表和公告表不会被旧版本访问，Redis 服务可以保留但不向宿主机公开端口。

- 单元测试覆盖通知类型注册、链接和正文校验、受众解析、去重、分页、已读策略和权限错误。

## 风险 / 回滚

- Redis 不可用时实时提示会失效，但通知写入和通知页读取必须继续工作；恢复 Redis 后在线用户可通过 SSE 重连获得后续提示，历史通知仍由 PostgreSQL 保留。
- 公告发布是批量收件人写入，需在事务中使用快照并设置合理批量大小；发布失败时不产生半成品通知。
- 已发布内容不可变，错误内容只能追加更正公告，避免修改已送达文本造成审计不一致。
- 回滚前备份数据库并保留 migration 历史；不得使用 `down -v` 删除生产数据卷。
